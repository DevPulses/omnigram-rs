# ==============================================================================
# TELEGRAM DESKTOP RUST (TDESKTOP-RS / OMNIGRAM-RS) — ПЕРЕНОС ИСХОДНИКОВ НА RUST
# ==============================================================================
# Концепция: системное пошаговое портирование оригинальной кодовой базы
# Telegram Desktop (C++20 / Qt) на Rust с сохранением архитектуры, протокола,
# структур данных (tdata) и 100% оригинального классического интерфейса TDesktop.

1. ГЛАВНАЯ ЦЕЛЬ И ФИЛОСОФИЯ
------------------------------------------------------------------------------
* Точная, чистая копия официального Telegram Desktop (TDesktop).
  Никаких сторонних модификаций — классический, привычный интерфейс TDesktop.
* Перенос реальной проверенной логики исходников C++ Telegram Desktop модуль за модулем.
* Избавление от многочасовой компиляции C++, Qt-оверхеда и риска падений по памяти.
* Старт приложения за доли секунды, потребление 30–50 МБ RAM вместо 500+ МБ.

2. СТРОГИЙ ПРИОРИТЕТ РАЗРАБОТКИ: СНИЗУ ВВЕРХ (ОТ ТЕХ. ЧАСТИ К UI)
------------------------------------------------------------------------------
* Задачи в графе зависимостей строго упорядочены по фундаментальной важности:
  
  [ПРИОРИТЕТ 1: ФУНДАМЕНТ] Криптография, бинарные буферы и TL-генератор типов.
    Без этого невозможно распаковать ни один пакет Telegram и ни один файл сессии.
  
  [ПРИОРИТЕТ 2: СЕТЬ И ХРАНИЛИЩЕ] MTProto транспорт (TCP) и чтение формата `tdata`.
    Результат: мы можем зайти в существующий аккаунт с диска и обмениваться пакетами с сервером.
  
  [ПРИОРИТЕТ 3: МОДЕЛИ ДАННЫХ И СОСТОЯНИЕ] HistoryItem, PeerData, диалоги, сообщения.
    Результат: все сообщения, пользователи и чаты корректно десериализуются и хранятся в памяти.
  
  [ПРИОРИТЕТ 4: ПАРСЕР СТИЛЕЙ И РЕСУРСОВ] Чтение `.style` файлов и палитры оригинального TDesktop.
    Результат: в коде появляются точные цвета, отступы, размеры шрифтов и геометрия.
  
  [ПРИОРИТЕТ 5: ГРАФИЧЕСКИЙ ИНТЕРФЕЙС (UI)] Отрисовка компонентов на экране.
    Результат: полноценный экран приложения со 100% визуальной идентичностью оригиналу.

* Агенты не переходят к рисованию UI, пока под ним нет рабочего и протестированного движка!

4. ПРАВИЛО УПРОЩЕНИЯ ОВЕРИНЖИНИРИНГА В C++ (SMART REFACTORING)
------------------------------------------------------------------------------
* В Telegram Desktop за 11+ лет накопилось огромное количество C++ оверинжиниринга:
  - Запутанные многослойные абстракции над Qt событиями,
  - Ручные менеджеры памяти, костыли для обхода старых ограничений C++11/14,
  - Чрезмерно усложнённые шаблонные макароны (template metaprogramming).
* ПРАВИЛО: ЕСЛИ В C++ КОДЕ ЕСТЬ ОВЕРИНЖИНИРИНГ И ЕГО МОЖНО УПРОСТИТЬ НА RUST,
  НО ПРИ ЭТОМ ВИЗУАЛЬНЫЙ РЕЗУЛЬТАТ, ПОВЕДЕНИЕ И ДИЗАЙН НЕ ИЗМЕНЯТСЯ НИ НА ПИКСЕЛЬ —
  ТОГДА УПРОЩАТЬ НЕ ТОЛЬКО МОЖНО, НО И НУЖНО!
* Как это работает на практике:
  - Идиоматичный Rust: заменяем запутанные циклы и указатели на чистые `match`,
    итераторы, `Option`/`Result` и компактные структуры данных.
  - Упрощаем внутреннюю кухню и архитектуру вычислений, но финальный рендеринг,
    геометрия, цвета и отклики на действия пользователя остаются строго 1-в-1 с TDesktop.

5. МУЛЬТИ-АГЕНТНЫЙ КООРДИНАТОР (CLI-УТИЛИТА `agent-hub` НА RUST)
------------------------------------------------------------------------------
* Для слаженной параллельной работы нескольких ИИ-агентов пишется легковесная CLI-утилита
  на Rust (`agent-hub` / `tasklock`), управляемая через флаги терминала.
* ПРЕДВАРИТЕЛЬНАЯ КАРТА ФАЙЛОВ И ГРАФ ЗАВИСИМОСТЕЙ (DEPENDENCY GRAPH MAP):
  - ПЕРЕД началом работы мы формируем глобальную карту файлов (`file_map.json`),
    где расписаны все модули TDesktop, их уровни приоритета (от фундамента до UI)
    и явные зависимости друг от друга (`depends_on`).
  - Эта карта загружается в `agent-hub`.
  - ЗАЩИТА ОТ КОНФЛИКТОВ СВЯЗАННЫХ ФАЙЛОВ:
    Если агент берёт задачу `A`, а модуль `B` тесно связан с `A` или зависит от него,
    `agent-hub` автоматически БЛОКИРУЕТ модуль `B` для взятия другими агентами до тех пор,
    пока базовый модуль `A` не будет полностью сдан и протестирован!
    Никаких ситуаций, где два агента одновременно пишут зависимые друг от друга части.
* Команды CLI для агентов:
  - `./agent-hub claim --id <task_id> --agent <agent_name>`:
    проверяет граф зависимостей, блокирует задачу и зависимые ветки.
  - `./agent-hub release --id <task_id>`:
    откат/снятие лока при ошибке или прерывании.
  - `./agent-hub complete --id <task_id>`:
    отметка об успешном завершении задачи; разблокирует следующие в графе задачи.
  - `./agent-hub status`:
    дерево графа задач с приоритетами: что готово, что в работе, кто занят, что заблокировано.
  - `./agent-hub next --agent <agent_name>`:
    выдача следующей свободной задачи наивысшего приоритета (от тех. части к UI).
* Локальное атомарное хранение состояния (`.agent-state.json`) с блокировкой файлов ОС (flock).

6. СТРОГАЯ ДЕКОМПОЗИЦИЯ И АРХИТЕКТУРА ФАЙЛОВ (MAXIMAL MODULARITY)
------------------------------------------------------------------------------
* Максимальное дробление кода на маленькие, сфокусированные файлы и подмодули:
  - Никаких монолитных файлов на тысячи строк кода!
  - Каждый файл решает ровно одну четкую задачу (Single Responsibility Principle).
  - Если в модуле появляется вспомогательная структура, алгоритм валидации,
    сериализатор или крипто-примитив — они сразу выносятся в отдельный файл.
* Иерархия модулей зеркалит логику компонентов TDesktop:
  - `storage/tdata/key_data.rs` — только чтение key_data.
  - `storage/tdata/passcode.rs` — только проверка и хеширование локального пароля.
  - `storage/tdata/settings.rs` — только десериализация настроек сессии.
  - `mtproto/crypto/aes_ige.rs` — только алгоритм AES-IGE.
  - `mtproto/crypto/auth_key.rs` — только вычисление AuthKey и идентификаторов.
  - `mtproto/transport/tcp_abridged.rs` — только протокол Abridged.
  - `ui/components/dialog_row.rs` — только отрисовка строки диалога.
  - `ui/components/unread_badge.rs` — только бейдж непрочитанных.
  - `ui/components/message_bubble.rs` — только отрисовка бабла сообщения с хвостом.
* Зачем это нужно:
  - Идеально для работы ИИ: маленькие файлы целиком помещаются в контекст без обрезаний.
  - Исключает забывание деталей и галлюцинации в UI логике.
  - Мгновенная инкрементальная компиляция `rustc` (перекомпилируется только один файл).
  - Удобство изолированного тестирования компонентов.

7. СТРОГАЯ ПОЛИТИКА ЗАВИСИМОСТЕЙ (ZERO-BLOAT & IN-HOUSE CODE)
------------------------------------------------------------------------------
* Принцип минимализма: НЕ тащить в проект тяжёлые монструозные крейты ради 1-2 функций.
* Использовать строго минимально необходимые версии зависимостей.
* Собственные реализации (In-house implementations):
  - Если для задачи нужен фрагмент функционала внешней библиотеки — пишем собственный
    легковесный вариант строго под наши нужды (свой генератор TL, свой крипто-слой,
    свои бинарные ридеры/райтеры, свой парсер стилей).
  - Никаких раздутых деревьев зависимостей (zero dependency hell).
* Максимальная автономность кодовой базы, сборка силами одного лишь `cargo`.
