# AGENTS.md — правила работы агентов над omnigram-rs

Порт Telegram Desktop (C++20/Qt) на Rust: точная копия классического интерфейса,
реальная логика переносится из оригинальных исходников. Исходники — в `tdesktop/`
(shallow-клон + сабмодули lib_tl/lib_ui).

## Жизненный цикл задачи (обязательно для каждого агента)

1. В начале работы взять задачу:
   ```
   ./target/release/agent-hub next --agent <имя>
   ```
   Команда атомарно выдает свободную задачу высшего приоритета и блокирует её
   вместе со связанными (`related`) модулями. НЕЛЬЗЯ брать задачи вручную в
   обход `next`, если только задача не назначена координатором явно.
2. Работать строго в пределах путей из выданной задачи (`paths`) и целевой
   директории пода `crates/<модуль>/`. Чужие модули не трогать — они могут быть
   заняты другим агентом.
3. По завершении:
   ```
   ./target/release/agent-hub complete --id <task_id>
   ```
   При ошибке или невозможности закончить:
   ```
   ./target/release/agent-hub release --id <task_id>
   ```
   (снимает лок, задача возвращается в пул).
4. Общее состояние — `./target/release/agent-hub status`. Смысл меток:
   `[✔]` сдано, `[▶]` в работе, `[*]` доступна, `[ ]` заблокирована зависимостями.

## Порядок работ (снизу вверх, не нарушать)

Граф в `file_map.json` упорядочен по приоритетам 1..5. Агент не переходит к
отрисовке UI, пока под ним нет рабочего и протестированного движка:

1. Фундамент: TL reader/writer/generator, криптография (AES-IGE, KDF, SHA, DH).
2. Сеть и хранилище: MTProto 2.0 TCP-транспорт, чтение `tdata`.
3. Модели данных: PeerData, HistoryItem, апдейты.
4. Стили и ресурсы: парсер `.style`/палитр.
5. UI: окна, списки, баблы, анимации — 1-в-1 с оригиналом.

Если задача заблокирована зависимостью, которую на Rust переносить не нужно
(например, хелперы Qt/`base/`, чья логика не нужна или покрывается stdlib) —
сообщить координатору, а не выдумывать обход. Координатор вырезает зависимость
из `file_map.json` вручную.

## Правила переноса кода

- **Источник правды — файлы `tdesktop/`.** Переносим семантику оригинала,
  а не придумываем поведение заново. Прежде чем писать, прочитать
  соответствующий .h/.cpp из выданных `paths`.
- **Idiomatичный Rust.** Оверинжиниринг C++ (многослойные абстракции над Qt,
  менеджеры памяти, шаблонная метапрограмма) упрощается, ЕСЛИ видимый
  результат — данные, поведение, рендеринг — не меняется ни на бит.
  `match`, итераторы, `Option`/`Result` вместо циклов с указателями.
- **Максимальная модульность.** Один файл — одна задача. Вспомогательные
  структуры, сериализаторы, криптопримитивы выносятся в отдельные файлы
  (`storage/tdata/key_data.rs`, `mtproto/crypto/aes_ige.rs` и т.д.).
  Никаких файлов на тысячи строк.
- **Зависимости — минимальные.** Не тащить тяжёлые крейты ради 1–2 функций.
  Свой код (TL-генератор, парсер стилей, бинарные ридеры) — пишем сами.
  КРИПТОГРАФИЮ собственными реализациями примитивов НЕ заменять: примитивы
  берутся из проверенных крейтов (RustCrypto/ring), собственным может быть
  только протокольный слой вокруг них.
- **Workspace-структура.** Каждая задача — отдельный крейт или модуль в
  `crates/` (смотреть `file_map.json` → `paths` в tdesktop — соответствие
  зеркалится в `crates/<id>/`).

## Верификация (у каждой задачи должен быть оракул)

Задача считается сданной (`complete`) только когда пройден её оракул проверки:

- крипто/бинарные форматы: бит-в-бит совпадение с выводом C++-логики на
  реальных данных (tdata-файлы, дампы пакетов);
- TL-типизация: разбор `tdesktop/Telegram/Resources/scheme.tl` и реальных
  сериализаций;
- парсер стилей: диф значений палитры/геометрии против оригинальных `.style`
  файлов и сгенерированных заголовков;
- UI: попиксельная сверка скриншотов с оригинальным TDesktop (если оракул
  невозможен — пометить задачу как «нужен визуальный ревью» в отчёте).

Тесты пишутся рядом с кодом (`#[cfg(test)]` или `tests/`). Команда агента
после каждого изменения:

```
cargo build --release && cargo test
```

Без прохождения тестов и оракула `complete` делать нельзя.

## Запреты

- Не менять `tdesktop/` (это read-only источник).
- Не менять priority, список задач и paths в `file_map.json` (только
  координатор).
- Не редактировать `.agent-state.json` вручную — только через agent-hub
  (flock защищает от гонок параллельных агентов).
- Не «рисовать UI на глаз»: каждый отступ, цвет, радиус, анимация берутся из
  оригинальных исходников `.style` и `ui/` файлов.
- Не коммитить и не пушить без указания координатора.
